## Key Architectural Insights

### 1. Compute Boundary (Verified)
- **ESP32 is the autonomous safety controller.** Not a dumb sensor node.
- **Steinhart-Hart calculations** run in C++ lambda on the MCU (not HA templates).
- **PID loop** runs every 2 seconds on the ESP32 (not Node-RED).
- **All 4 safety interlocks** evaluate in the 2s loop, on-device, with no remote dependencies.
- **Result:** HA outage or network loss does NOT interrupt an active brew.

### 2. Multi-Stream Flow Control (Unique Design)
- **Display stream:** `an1_rate` = median(5) + EMA(α=0.25) ≈ 4–5s lag. Smooth, readable on dashboard.
- **Safety stream:** `an1_flow_safety_v` = median(3), no EMA ≈ ~2s lag. Fast enough to catch sudden pump failure before RIMS element scorches.
- **Why this matters:** A single EMA-smoothed flow sensor would be too slow to protect against dry-firing. Dual-stream design separates concerns (display vs. safety).

### 3. Safety Model (Complete Chain)
- **Guard 0:** Staleness watchdog (8s) — catches I²C bus wedge
- **Guard 1:** NAN guard — catches sensor disconnect/fault
- **Guard 2:** Over-temp (>90°C) — catches pump failure or sensor malfunction
- **Guard 3:** Flow interlock (armed, commissioning-gated) — catches scorch risk
- **Edge-guarded publishes** keep HA logbook clean (one event per state change, not every 2s cycle)
- **Hardware cutoff** (REQUIRED, external): Bimetallic/fuse in series with mains load — independent last-resort protection

### 4. Offline Persistence (Elegant Solution)
- **Challenge:** Serial console logs are ephemeral; HA logbook is persistent. But HA is not always online.
- **Solution:** Publish every significant event to a text_sensor entity. HA recorder stores state changes to its local DB (on Pi), independent of transport. When HA comes back online, it logs all buffered state changes.
- **Result:** Safety events and user actions are logged to the permanent logbook even if the ESP32 was offline when HA comes back.

### 5. Firmware-HA Role Separation (Clear)
- **ESP32 (autonomous):** Acquire sensors, run math, control heater, enforce safety, persist state to flash.
- **HA (supervisory):** Display, config UI, parameter persistence via cloud sync, offline logbook.
- **Node-RED (planned):** High-level brew sequencing (mash steps, timers). Does NOT run the control loop (that stays on ESP32).
