# singularity v1.0.5 — RIMS toggle switch refactor and PID-only control

The v1.0.5 change replaces the `select` entity (OFF/PID mode) with a `template switch` (`rims_heater`) as the control interface for the RIMS PID loop. The `slow_pwm` output on GPIO42 remains exclusively owned by the interval control loop. The PID math is sound: incremental form with anti-windup and a NaN safety shutoff. The main problems are dashboard entity references that were not updated to match the firmware refactor, two orphaned number entities that are never read by any control logic, and a missing newline that concatenates two log lines in the compiled firmware.

Watch for:
- **confirmed** — `select.singularity_rims_mode` (deleted from firmware) still referenced in the Settings card; the control will show as an unavailable entity in HA.
- **confirmed** — `switch.singularity_ssr2` referenced in the Log tab SSR Activity graph; no such switch entity exists (GPIO42 is a `slow_pwm` output, not a gpio switch).
- **confirmed** — `sensor.singularity_firmware_version_display` referenced in the Activity Log and the About tab version table; the firmware exposes this as `sensor.singularity_build`. Broken since dashboard v1.0.3.
- **confirmed** — `dc_duty_cycle` and `pid_switch_threshold` number entities remain in the firmware, persist to flash, and surface to HA, but are never read by any lambda.
- **likely** — no upper temperature runaway guard; a shorted NTC returns a plausible low reading and the PID drives the heater at full duty indefinitely.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The firmware refactor from `select` to `template switch` is self-consistent: the interval loop checks `id(rims_heater).state`, the `on_turn_on`/`on_turn_off` callbacks reset PID state, and the `slow_pwm` on GPIO42 is the only writer to that pin.

The dashboard was partially updated. The main Brewing Temperatures tab correctly references `switch.singularity_rims_heater`. The Settings tab RIMS card still points to the deleted `select.singularity_rims_mode`, and the Log tab SSR Activity graph references `switch.singularity_ssr2`, which has never existed as a switch entity in this firmware. Both will show as unavailable in HA on deploy.

`sensor.singularity_firmware_version_display` has never existed in the firmware — the text sensor is named `"Build"`, giving `sensor.singularity_build`. The wrong ID was introduced at dashboard v1.0.3 and has propagated through four subsequent dashboard releases.

Two number entities (`dc_duty_cycle`, `pid_switch_threshold`) survived the v1.0.4 removal of DIRECT mode. No lambda reads them, but they persist to flash and appear as configurable parameters in HA.

The NaN guard shuts the heater off on open-circuit sensor failure, but a shorted NTC returns a falsely low temperature reading, keeping the PID at full output with no cutoff.

<summary>Details</summary>

### Stale `select.singularity_rims_mode` in the Settings RIMS card

The v1.0.5 firmware commit deleted the `select` platform entity (`id: rims_mode`) and replaced it with a `template switch` (`id: rims_heater`, `name: "RIMS Heater"`). The Settings tab RIMS Heater card was not updated: line 236 still lists `select.singularity_rims_mode`. In HA this renders as an unavailable entity widget — the card displays but the control does nothing. The correct entity is `switch.singularity_rims_heater`.

### `switch.singularity_ssr2` in the SSR Activity history graph

The Log tab's SSR Activity `history-graph` card lists `switch.singularity_ssr2` (line 134). GPIO42 is declared as a `slow_pwm` output and is only ever written to by the interval lambda; no `gpio switch` has ever existed on this pin in any firmware version. The graph will show SSR1 activity and an empty/unavailable trace for SSR2. `switch.singularity_rims_heater` can approximate RIMS heater state (it reflects PID enable, not individual PWM pulses).

### `sensor.singularity_firmware_version_display` entity ID mismatch

The firmware text sensor is `name: "Build"`, which ESPHome slugifies to `sensor.singularity_build`. The dashboard references `sensor.singularity_firmware_version_display` in two places: the Activity Log logbook (line 126) and the About tab version table Jinja template (line 272). The `_display` suffix variant does not exist anywhere in the firmware's git history — it was introduced as a wrong name at dashboard v1.0.3 and has not been corrected across four subsequent dashboard releases.

### Orphaned DIRECT mode number entities

`dc_duty_cycle` (RIMS Direct Duty Cycle) and `pid_switch_threshold` (RIMS PID Switch Threshold) were added in v1.0.3 for the dual-mode DIRECT+PID design. The v1.0.4 commit removed the interval lambda logic that read them, but the number entity definitions remain. They persist to flash and appear in HA's entity registry, surfacing as apparently meaningful tuning parameters to anyone working on the controller.

### on_boot lambda formatting defect

Line 92 of the firmware has the RIMS heater log call and the SSR1 log call concatenated on one source line with no newline:

```
id(rims_heater).state ? "ON" : "OFF");          ESP_LOGI("singularity", "SSR1: ...
```

The lambda is syntactically complete and both `ESP_LOGI` calls execute. The risk is that a future edit to this line (e.g. changing the format string) trims trailing content and silently drops the SSR1 log statement.

### Runaway guard gap for shorted NTC

The interval lambda guards against `std::isnan(temp)` and shuts off the heater, which handles open-circuit disconnection correctly. A shorted NTC presents near-zero voltage to the ADS1115; the Steinhart-Hart lambda passes the `v > 0` guard, computes a resistance that maps to a very low (but numerically valid) temperature, and the PID responds by driving maximum duty. There is no upper temperature cutoff. Adding `if (temp > 90.0f) { id(rims_heater_pwm).set_level(0.0f); ESP_LOGW(...); return; }` before the PID block would close this. The `temp < -10 || temp > 150` range check in the NTC filter lambda would catch the extreme case but only produces NaN at >150°C — everything between the true mash temperature and 150°C is treated as valid feedback.
